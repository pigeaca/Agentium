# Automation A2: a task pool that keeps itself fresh (wave 4)

- Date: 2026-10-02
- Status: Planned (2026-10-02), awaiting the user's answers to the open questions. Planning only: no code yet.
- Scope: section 1 of the [automation plan](2026-10-01-automation.md). After `git pull` the pool gains new tasks, re-checks old ones and retires dead ones, with no agent runs and no cost. It builds on [task mining](archive/2026-10-01-task-mine.md) and on A1 (headless mode, `--json`; "per A1" below means the contract in `docs/guide.md`, "Scripting and automation").

## Outcome and boundaries
- **`agentium pool update [--background]`** does four things, in this order, and runs no agent:
  1. **Mine** since the last pass (`task mine --since`), importing up to `--limit` (default 10) new candidates as tasks that need review.
  2. **Validate** the new tasks in a batch (`--jobs`, default 1 in the background, 2 in the foreground).
  3. **Re-validate stale tasks.** A task is stale when its last validation (a) is older than 30 days, (b) was made with other build-tool versions than today's (Go, Maven, Gradle, Cargo: new `Validation.Toolchain`, a JSON field, so no migration), or (c) is `flaky` and has not been retried for 7 days. Claude Code's version is *not* a reason: validation runs only the build and the tests, never an agent (see Contradictions).
  4. **Retire** a task when its base commit is older than 270 days, or when the files it names (reference or hidden tests) no longer exist on the default branch's head. Retiring is a flag with a reason, never a delete: runs and locked experiments keep their rows. Retired tasks leave the eligible set and the health counts' "valid".
- **Pool health:** `agentium pool status` and the end of every update print counts: valid, flaky, weak (valid with a weak-tests warning), awaiting review, invalid, retired, plus the last pass's time and the oldest valid base. `--json` follows A1's contract (stable keys, exit codes 0/1/2, no prompts).
- **Review gate:** mined tasks stay "awaiting review" until `task edit NAME --reviewed`. The pool never accepts on its own. `--accept-mined` matches `start`'s: it accepts only tasks this pool pass imported (kept in the same kind of state file as `start-mined.json`), only after the automatic fairness checks, and holds back any with an unstated requirement. It is off unless given (A1's `agentium.toml` may set it, never default it on).
- **Concurrency:** background jobs queue instead of failing.
  - **Queue:** a directory `queue/` in the data folder, one JSON file per job (`kind`, project id, enqueue time, attempts), written by temp file and rename. At most one pending `pool-update` per project: a newer trigger refreshes the file. At most 50 pending files; jobs older than 7 days expire.
  - **Consumer:** whoever enqueues tries `queue.lock` (flock, non-blocking). The winner detaches (own session, output to `queue/pool.log`, rotated at 1 MiB), drains the queue one job at a time, re-scans after the last job, then releases. A loser exits at once: its file is already there. A job file is deleted only after its job ends, and the job is idempotent (mining skips existing tasks; validation stores only while the task's commands are unchanged).
  - **Crash:** the OS drops the flock. The next trigger finds the file with `attempts` raised, and runs it again. After 3 attempts the file moves to `queue/failed/` and `pool status` shows it. Half-written files (`*.tmp`) older than an hour are removed.
  - **Busy runs:** validation does not take the run lock today (see Contradictions). A background job waits while `RunsBusy()` is true (re-checks every 30 s, up to 2 hours, then re-queues), so experiments are not slowed. A foreground `pool update` only warns, like `task validate` does. The queue is generic (`kind`), so A4's cost screen reuses it.
- **`agentium hooks print git`** prints `post-merge` and `post-rewrite` scripts. Each runs the repository's existing hook first (and honors its status), then `agentium pool update --background` with output discarded, and always exits 0, so Agentium can never fail or slow a `git pull`. `post-rewrite` acts only for `rebase`. The script holds the absolute path of the binary and no commit-derived text. Agentium never writes `.git/hooks`, `core.hooksPath` or settings; the user installs them, as with `context lint --print-hook`.
- **Triggers:** `post-merge`, `post-rewrite`, and the scheduled pass (A5's `watch --once` calls the same update). Not `FETCH_HEAD`.
- **Compatibility:** one new migration (next free number), adding `retired_at` and `retired_reason` to `tasks`. Existing tasks, experiments and exit codes do not change. Experiments' eligible-task selection excludes retired tasks, and locked experiments keep the tasks they locked.
- **Not in scope:** agent runs, paid calls, writes to the user's repository or settings, `launchd` (A5), PR comments (A4), Codex.

## Acceptance
1. **After `git pull` and after `pull --rebase`** with the printed hooks installed, the pool gains the new commit's task as "awaiting review", validated, and no agent was started. *Evidence:* a CLI test with a fixture repository and fake hooks input, then a real console sample on Agentium's own repository.
2. **Stale and retired tasks** follow the rules above, each with its reason in the table: tests with a fake clock and fake toolchain versions, including the boundaries (29/31 days; 269/271 days; a deleted reference file).
3. **Health** is printed and in `--json` per A1; the JSON keys are fixed by a test.
4. **Queue:** two simultaneous triggers run one pass; a trigger during a running pass is picked up before the consumer exits; a kill at each step (after enqueue, mid-job, before delete) is recovered by the next trigger without a duplicate task or a lost job; the 3-attempt and 50-file limits hold; the queue waits out a busy run lock.
5. **Review gate:** a mined task is never accepted without `--accept-mined`, which accepts only this pass's imports and holds back tasks with gaps; a corrupt state file costs only that shortcut, as in `start`.
6. **Hooks:** the printed scripts chain this repository's `.githooks`-style existing hook, exit 0 when Agentium fails or is missing, never write anything, and pass `shellcheck`-style review (a test runs them under `sh` with a fake `agentium`).
7. **Docs:** the guide's task-pool and hooks sections, the architecture's code map (`internal/pool`), and the automation plan's status.

## Open questions for the user
1. **Defaults:** 30 days stale, 270 days base age, up to 10 imports per pass. Keep, or change? (They go to `agentium.toml` under A1.)
2. **Background validation concurrency:** 1 job and deferral while experiments run (slower, safe), or 2 jobs and no deferral?
3. **Retirement by age alone** retires tasks that are still valid and useful. Is age-only retirement right, or should age only flag ("old") and retire only on deleted files?
4. **Weak-tests check** in the background pass (extra builds per task): default off, on only with `--weak-tests`?
5. **Re-validating a flaky task** with `--repeat 3` costs 3x the time. Should background passes retry flaky tasks at all, or leave them for a manual run?

## Contradictions with the automation plan (from the code)
- **"Jobs queue rather than fail on a busy lock":** validation and mining never take `runs.lock`; only agent runs do (`cli/run.go`), and `RunsBusy()` only annotates the batch table. So `ErrBusy` is an A4 problem. A2 needs its own `queue.lock`, plus a policy for waiting out running experiments (above).
- **"Stale: Claude Code change":** validation runs no agent, so a Claude Code change cannot stale it. The code records no toolchain versions either, so (b) needs a new field.
- **"Since last":** nothing stores a mining watermark today (`mine` skips by existing task commits). It needs new state.
- **"Retire":** the schema has no retired state; it needs the migration.
