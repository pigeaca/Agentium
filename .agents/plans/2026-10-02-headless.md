## Outcome and boundaries
Hooks and schedulers (the later phases) can call Agentium without a person: machine-readable output, fixed exit codes, and no prompt that could wait forever.

**Part 1 (built now), these commands only:** `init`, `context show|snapshot|list|diff|lint`, `task list|show|mine|validate|import|add|edit|rm`, `run once|show|list`, `start`.
- Not touched: `internal/cli/experiment*.go`, `internal/report`, `internal/experiment` (the `seq-v1` engine owner has them), and the Accepted list in `start_tasks.go`. `run calibrate` and the experiment commands keep human output only.
- **Part 1b (after the `seq-v1` work merges):** `--json` for `experiment new|plan|show|run|list|...` in the same contract (`experiment report` already has its own JSON), and `start --json --yes` (which runs an experiment).
- No new modules (`encoding/json`). No change to data on disk, no credential handling, no paid run.

**Part 2 (later, its own high-risk step; described only):** a committed `agentium.toml` that Agentium reads and never writes. It would carry what automation needs and must not guess: weekly and per-check budgets, consent to spend (which triggers may run paid work), task selection, the judge setting. Because it grants consent to spend money from a file a teammate's commit can change, it needs its own threat review: who may change it (refuse changes by others in automated mode, as for harness settings), no secrets in it, a closed set of keys with unknown keys rejected, and values that only lower what flags allow unless the user's own flags raise them. Parsing needs a TOML reader, so it needs a dependency approval first.

## The contract
- `--json` (bare, anywhere before `--`) makes the command print exactly one JSON document on stdout, then exit. Human text is not printed; progress and live status lines are off; warnings that matter are in the document.
- Top level: `"schema"` (integer, 1; it rises only on a breaking change; adding fields is not breaking) and `"command"` (e.g. `"task list"`). Field names are stable snake_case. Lists are `[]`, never `null`.
- Errors: `{"schema":1,"command":...,"error":{"message":"...","code":N}}` on stdout, `code` equal to the process exit code. Usage errors give a short message (run the command with `-h` for usage). The home folder in a message is shown as `~`.
- No ANSI color, ever (`NO_COLOR` and `FORCE_COLOR` are irrelevant). Terminal width is not used.
- Redaction as in reports: project name, short commits and relative paths of repository files only; no absolute paths (repository, data folder, records, Claude Code binary) and no user names.
- `--json` with `-h` prints the usage as without it. `context lint --hook/--print-hook` already print their own JSON and refuse `--json`.

## Exit codes
| Code | Meaning |
|---|---|
| 0 | Success. Includes "nothing to do": no tasks, no candidates, no differences, `start` stopping at its preview. `context lint` always exits 0 for findings. |
| 1 | Runtime failure: the command could not do its job, or its result is bad: an invalid or flaky task, too few tasks for `start`, a start that was asked to run (`--yes`) while not ready. |
| 2 | Usage error: bad flags or arguments. |

No further code now. A "blocked, needs review" code (for example 3 for `start` when tasks wait for a human) was considered and rejected for part 1: nothing consumes it yet, it would change the exit code of existing human-mode behavior that tests and another in-flight fix assert, and the JSON document already says why (`status`, `ready`, the readiness checks). Revisit in A2 (the pool) when a caller needs to branch on it.

## No prompts
The only prompt is `start`'s "Run it now?" in `confirm`. It asks only when stdin and stdout are both terminals, so a non-terminal stdin never blocks; this part makes that a documented contract and tests it (also for `--json`, which never asks, even on a terminal). Without `--yes` it stops at the preview with exit 0 and says nothing was run; `--yes` is the only way to spend. No other command reads stdin except `context lint --hook`, which reads a bounded payload.

## Acceptance
1. With `--json` each listed command prints one valid JSON document with `schema` and `command`; shapes and field names are fixed by table tests.
2. Failures print the error object with the matching exit code; usage errors exit 2 with an error object; success exits 0; invalid/flaky validation exits 1 with the result document.
3. `NO_COLOR` and `FORCE_COLOR` do not change JSON; no document contains an ANSI escape or an absolute path of the repository or data folder.
4. `start` never blocks on a non-terminal stdin and never asks with `--json`; `start --json --yes` is refused with a usage error (part 1b).
5. Human output of every command is unchanged without `--json` (existing tests pass untouched).
6. The contract and exit codes are in `docs/guide.md` ("Scripting and automation").
