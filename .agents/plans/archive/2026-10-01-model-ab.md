# Model and effort comparison for Claude Code

- Date: 2026-10-01
- Status: Done (2026-10-02): steps 1–2 in #74 and #75; step 3, the real check, was the wave-2 external verdict below (approved by the user on 2026-10-02).
- Scope: on 2026-10-01 the user asked to plan the next features and to skip Codex. This is the part of [Phase 2](2026-10-01-phase2-agents-codex.md) that needs no Codex: comparing models, or effort levels, of Claude Code on the user's own tasks.

## Why
- **Which model or effort?** Users choose a model (Sonnet or Opus) and an effort level for their repository, and Agentium measures only context today.
- **What it costs:** model and effort change both success and cost more than context does, so a paired comparison with the same statistics and honest verdicts answers a question users actually have.

## Outcome
- `experiment new NAME --template model-ab --a MODEL[:EFFORT] --b MODEL[:EFFORT] [--context NAME]` compares two Claude Code profiles on the same tasks and context.
  - For example `--a claude-sonnet-5-5 --b claude-opus-5-5`, or one model at `--a claude-opus-5-5:medium --b claude-opus-5-5:high`.
  - Both arms use one context (the base's own, or a snapshot).
- **Preview:** each arm is estimated from the project's past runs on its own model (`EstimateRun`), or from the default profile. Each arm has its own cap, and the budget holds both.
- **Calibration and locking:** calibration runs per model, the lock records each arm's model and effort, and drift is checked per arm.
- **Reports** name each arm by its profile. Verdicts read as for context, for example "B (opus, high) costs 2.3× more and succeeds no more often". The noise note names the model it was measured on.
- **Unchanged:** the context A/B and A/A templates.

## Design
- **Arms:** `Arm` gains `Model` and `Effort` (json `omitempty`), so earlier designs and locks read the same.
  - `Design.Model` and `Design.Effort` stay the default for both arms.
  - `model-ab` requires the arms to differ in model or effort, and to share a context.
  - Context templates refuse per-arm models.
- **Runs:** the run spec takes the arm's model and effort. Everything else (isolation, grading, judge) is unchanged.
- **Calibration:** today it is per experiment on one model. It becomes per arm when the models differ, as two calibration runs, since tools and skills can differ by model.
- **Analysis:** no change. The paired statistics already compare arms. The cost margin stays relative.
- **Pricing:** list prices per model already exist (`internal/pricing`). The preview flags a model with no price.

## Acceptance
1. **Design:** `model-ab` is validated (different profiles, one context; a context template refuses per-arm models) and locked. Old designs and locks still load. *Evidence:* unit and CLI tests.
2. **Preview:** each arm is estimated on its own model, and the budget and caps hold both arms. *Evidence:* CLI tests with past runs on two models.
3. **Execution:** each run uses its arm's model and effort, calibration runs per model, and drift is checked per arm. *Evidence:* tests with a fake Claude Code that records its `--model` and `--effort`.
4. **Reports:** arms are named by profile, in all three formats. Reports of context experiments are unchanged (golden files). *Evidence:* golden tests and a real console sample.
5. **Real check (paid; approval):** `model-ab` with Sonnet against Opus on 4 tasks × 1. Every run is graded, and the report reads correctly. *Evidence:* the console sample and costs in this plan.
6. **Docs:** README (templates) and help.

Each code step is one PR with green CI and a review.
- [x] **1. Design, preview and execution** (2026-10-02; PR pending review).
  - **How it works.**
    - `Arm` gains `Model` (JSON `requested_model`, since a `LockedArm` embeds `Arm` and records the model its calibration saw as `model`), `Effort` and an optional `RunBudgetUSD`; all `omitempty`.
    - An arm with a model runs on that model and its own effort, so a default effort never leaks into the other arm. `Design.Model` and `Effort` are arm A's, for readers of one model.
    - `experiment new NAME --template model-ab --a MODEL[:EFFORT] --b MODEL[:EFFORT] [--context NAME] [--run-budget-a/-b USD]`. Validation: the arms differ in model or effort, share one context, and take one of `low, medium, high, xhigh, max`. The code had no effort list; this one is Claude Code's `--effort` set. Context templates refuse per-arm models and caps.
    - Preview: `EstimatesFor` estimates each arm on its own model, `PreviewFor` and `DefaultBudgetFor` add the arms' costs and caps, and a model without a list price is a readiness warning. `Reserve` holds the larger cap; the scheduler reserves each arm's own (`Plan.ArmCapUSD`).
    - Readiness and the lock use the newest calibration on each arm's model (`Project.CalibrationFor`, from the new `Store.Calibrations`); a missing one names `run calibrate --model M`. Drift compares a run with its own arm's calibration. Per-model calibration runs inside an experiment are step 2.
    - A model-ab design is stored as version 2 (context designs stay 1), so an older Agentium refuses it. Run records carry the requested `effort`, and estimates match on model and effort once any of the model's runs records one. Usage estimates are not split by model or effort (the plan says so). Context experiments find their own model's calibration.
    - Reports (step 2 does the rest): only the heading and the summary line name the arms' profiles, so that they do not show arm A's model for both.
- [x] **2. Calibration per model, and reports** (2026-10-02, branch `claude/feat/calibrate-in-run`, with quick-start step 2).
  - **How it works.**
    - **Calibration:** `experiment run` calibrates each distinct context and model it lacks, once, before the first pair: a model A/B makes two (one per model), a context A/B one per context, an A/A one. It is the quick-start step's mechanism ([how it works](../2026-10-02-quick-start.md)); each calibration is on the arm's requested model, so the lock's arm check compares a run with its own model's tools.
    - **`run once`:** `checkAgainstCalibration` uses `Project.CalibrationOn` (the context on the run's `--model`). Only without one does it use the newest of any model, with the old note that the model differs.
    - **Reports** (`internal/report/profiles.go`): in a model-ab report every arm label is its profile ("A (claude-opus-5-5:high)"): the metric table, cost-and-context table, context use, behavior, per-task headings, the judge rows and the pass line. Headlines read "Cost of B (P) vs A (Q) -48%" and "Success: A (Q) 60% → B (P) 55%". `Report.Summary` is the one-line verdict, for example "B (claude-sonnet-5-5) costs 48% less; success: exploratory.": a ratio metric with a verdict states direction and size, any other result is "name: verdict". The noise note says it was measured on both profiles together and pools two models' noise (the noise is estimated from the paired runs of both arms, not per model). JSON gains `arms[].profile`, `tasks[].arms[].profile`, `judge.arms[].profile` and `summary` (all `omitempty`, so context reports and their goldens are unchanged).
  - **Tests:** `report/profiles_test.go` (all three formats, the JSON, the summary's phrases, and a context report with none of it) and the CLI's `TestModelABCalibratesBothModels` and `TestRunOnceUsesItsOwnModelsCalibration`.
- [x] **3. Real check (paid; approved):** the wave-2 external verdict, `opus-vs-sonnet` on [samber/lo](https://github.com/samber/lo) (MIT): Opus 5.5 (A) against Sonnet 5.5 (B), 8 mined tasks × 1 run per arm. Full report: [model-ab-report.md](../../../docs/examples/model-ab-report.md).
  - **Cost: improved, −63% (95%: −70% to −53%)**: $0.269 per Opus run against $0.101 per Sonnet run. It is the project's first decisive verdict.
  - Success 50% → 75% and time −49% are exploratory at this size.
  - **Spend:** $3.10 for the 16 runs, plus $0.24 for the two calibrations, against a $36 estimate (the default profile assumed bigger tasks). Every run was graded, and no run was unfair or failed on infrastructure.
  - **Before the run, the tasks needed this:**
    - 13 mined and validated with 3 repeats.
    - samber/lo's timing tests (`WithDelay`, throttle, debounce, `WaitFor` and the like) fail under load, so tasks verify with `go test -skip '…' ./...`.
    - 3 instructions were trimmed of solution hints (Nth, Ellipsis, DropByIndex).
    - 8 clean tasks were chosen.
  - **Behavior:** Opus changed twice the lines (93 against 47 on average) and drew 9 Claude Code permission denials against Sonnet's 3.
